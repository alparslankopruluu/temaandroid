You are kicking off a new app from the app-factory kit. The product idea: **$ARGUMENTS**

Work through the phases below IN ORDER. Do not skip gates. Do not write feature code until the Bootstrap phase.
Use `/factory-run` (portable: `$source-command-factory-run`) instead when the user wants
one blueprint followed by automated infrastructure/assets/internal TestFlight
orchestration.

Set `python3 scripts/factoryctl.py run stage discovery` before intake/interview. After an
opportunity `go`, set stage `planning`; before Phase 6 set stage `build`. Stage changes
describe lifecycle only and never bypass a gate or authorize an external write.

## Phase 0 — Intake (if present)

If `app-intake.md` exists in the project dir (generated by the kit's `intake.html` form), read it first and use it to **pre-fill** everything below — do NOT re-interview the user on anything it already answers. Only ask about genuine gaps or fields marked `(decide)` / "Let the agent recommend". Then jump to the gates to confirm the agent-decided choices.

Also honor its **Existing code** field: if a repo URL/path is given, **read and adapt that repo** (detect its stack, wire the kit's docs onto its real structure, never blindly scaffold over it); if blank, scaffold fresh as normal. If there is no `app-intake.md`, run the full interview below.

## Phase 1 — Interview

Restate the idea in one sentence; let the user correct it. Then ask (one AskUserQuestion round, max 6 questions):

1. Who is the target user, and what painful moment makes them open the app?
2. What is the ONE core action the user will repeat? (This becomes THE core feature.)
3. Which existing apps solve this, and what is our wedge/differentiator?
4. Does the core action consume per-use backend cost (AI calls, media processing)? If yes, does it generate or edit media? *(→ monetization + fal.ai gate)*
5. Is Android planned within ~6 months, and do you want a later native Kotlin parity
   app or explicitly prefer one Expo cross-platform codebase now? *(→ stack gate)*
6. Any must-have native integrations (widgets, HealthKit, Live Activities, watch)? *(→ stack gate)*

## Phase 2 — Strategy and decision gates

Read `docs/playbooks/product-strategy.md`. Research at least five direct competitors
plus relevant substitutes from public store listings/reviews, product sites, pricing,
update history, public Reddit/X discussion when available, and public ad-transparency
libraries; evidence every claim and label assumptions. Paid market-intelligence tools
are not required or used by default. Fill the opportunity fields in PRODUCT.md and score with
`python3 scripts/opportunity_score.py score ...`.

- Only `go` may continue.
- `reposition` or `no_go` stops before product approval/code. Propose a narrower ICP,
  stronger wedge/channel, or monetization change; research and re-score the revision.
- Never invent TAM, search volume, revenue, CAC, LTV, or conversion data.
- Record downloads, revenue, ad spend, or organic growth as `unknown/assumption` unless
  public evidence supports them. Test the one-sentence core job, honest three-second demo/
  before-after proof, and video-ready core state inside the existing score dimensions.
- Run the tarpit/clone screen and the gotcha-moment one-sentence test from
  `docs/playbooks/product-strategy.md` before scoring; a failed clone screen is a
  critical risk (`--critical-risk`).

**Gate 0 — Opportunity.** Show evidence, all eight scores, total, weak dimensions,
category/review risk flags, and the recommended go/reposition/no-go decision.

**Gate 1 — Core backend usage.** Factory mode always provisions the standard Firebase/web/admin/R2/push operational surface. Decide whether the core feature also uses Firestore/Storage/Functions: local utilities keep domain data local; AI apps, accounts/sync, Model B, or paid-API proxies use the full backend path (→ `docs/playbooks/firebase.md`). Log the boundary.

**Gate 2 — Stack.** Recommend with reasoning, user decides. SwiftUI is the factory's
default first product stack; Android intent alone never auto-selects Expo:
- **SwiftUI-first + later native Android parity** for maximum iOS polish, native-heavy
  APIs, or the standard factory path. Record Android in the backlog, ship and verify iOS,
  then use `/port-android --scope=shipped --through=internal` to create the separate
  Kotlin/Jetpack Compose app under `android/`.
- **Expo RN** only when the user explicitly chooses one cross-platform TypeScript
  codebase/OTA workflow, or the intake points to an established Expo repo that should be
  continued. Explain the native-polish and platform-divergence tradeoff before approval.
- **Web-first (Next.js)** when the product *is* the website rather than an app that has
  one: organic search or content is the primary distribution channel, the value is a
  browsable corpus, a tool that needs no install, or a marketplace. Not for "we also want
  a web version" — that stays a Scope Fence exclusion. Before recommending it, state the
  tradeoffs plainly: no App Store distribution or ranking surface, **no payment rail in
  this kit** (RevenueCat/StoreKit are App Store rails — a web payment vendor is a separate
  documented decision and approval, so v1 is normally free), and organic search is slow to
  compound. If selected, read `docs/stack/web.md`, `docs/playbooks/web-design.md`, and
  `docs/playbooks/seo-content.md`; the App Store gates in Phases 5–6 do not apply.

If SwiftUI is selected, read `docs/playbooks/ios-expert-tools.md`. Focused external
skills are optional accelerators, never prerequisites: use `swiftui-pro` at meaningful
screen/feature reviews, `swift-concurrency-pro` only for async/actor/Sendable work, and
`swift-testing-pro` when writing/reviewing Swift Testing. Use `swiftdata-pro` only if the
approved persistence decision selects SwiftData. Never load all of them for every edit.

**Gate 3 — Monetization.** Read `docs/playbooks/monetization.md`, then recommend:
- Per-use backend cost → **Model B** (hybrid subscription + credits).
- Flat cost to serve → **Model A** (subscription-first, trial on annual).
Propose concrete price points from the pricing ladders. User decides.

## Phase 3 — Product definition

Fill **PRODUCT.md** completely: pitch, persona/trigger, evidence-backed positioning and
opportunity score, core-feature quality bar, vision/non-goal, monetization/unit economics,
distribution thesis, success/kill criteria, and launch locales (default nine; see localization playbook).

Fill `docs/product-map.md` with the core journey and every required screen/state,
analytics event, accessibility requirement, and measurable acceptance proof. Fill
`docs/security-model.md` from the data/SDK inventory and category flags. Fill
`docs/growth-plan.md` with the north star, funnel sources, primary channel, first-three
screenshots (the first two carry the strongest benefits), three-second organic hook,
real product proof, creative hypotheses, six-week launch calendar, and ranked experiment backlog; unknown
baselines stay `unknown`. Read `docs/playbooks/app-store-growth.md` and also record the
product-page narrative, supported store locales, CPP audience/intent+keyword/creative/
deep-link/analytics mapping, one-variable PPO hypothesis/sample/duration/stop, In-App
Event opportunity or its N/A reason, and preview-only header/search-result creative.

For a broader but coherent MVP, define the core **value system** around the wedge: core
action, recovery states, instrumentation, onboarding/paywall, and at most one retention
loop (saved progress/history, reminder, or a shareable result). Each element must reinforce
the repeat core job and have a measurable acceptance criterion; unrelated utilities remain
in the backlog. If AI media is selected, read `docs/playbooks/ai-media.md`, choose generate
or edit, record per-success cost, and require server proxy + Model B credit safeguards.

The strategy/product-document phases may be delegated as bounded `cloud_safe` work only
under `docs/playbooks/remote-execution.md`. Kit specialization, source integration,
Xcode/Simulator, provider auth/provisioning, signing, asset capture, and TestFlight are
always Mac-local. The local root reviews/merges remote diffs and owns all state updates.

Run the compact CEO → Product Owner → Design → Tech Lead → Security/Review → Growth
consistency review from the strategy playbook. If running under Claude Code, also spawn
the `spec-consistency-reviewer` subagent for a fresh-context pass over PRODUCT.md,
`docs/product-map.md`, `docs/security-model.md`, and `docs/growth-plan.md`, and fold its
findings into what you show next. **Gate 4:** show PRODUCT.md plus concise
product-map/security/growth summaries; iterate until approved.

## Phase 4 — Kit specialization (pruning)

1. Keep the chosen stack doc: move (`mv`, git comes later) `docs/stack/<chosen>.md` → `docs/stack.md`; delete `docs/stack/` entirely.
2. Fill EVERY `{{PLACEHOLDER}}` in CLAUDE.md, AGENTS.md, PRODUCT.md, and all `docs/` files — including playbook tokens (`{{BUNDLE_ID}}`, `{{APP_SLUG}}`, `{{CORE_ACTION}}`). `{{BUILD_CMD}}` = the daily dev-run command (e.g. `npx expo start`); release builds stay in the release checklist. Templates say "add lines as needed" — slot counts are minimums, not caps. Verify with `grep -rn '{{' CLAUDE.md AGENTS.md PRODUCT.md docs/`; the ONLY acceptable leftovers are code syntax: `{{count}}` (i18next, localization.md) and `options={{ offering }}` (JSX, paywall.md).
3. Seed `docs/architecture.md` fully: folder tree from `docs/stack.md` + service rows + state approach + nav map.
4. Log every kickoff decision (stack, monetization model, component foundation, state approach) as rows in `docs/decisions.md`.
5. Fill the **Design Direction** block in `docs/playbooks/design.md`: 3 personality adjectives + 2–3 reference apps (propose from the product's category; user picks) + concrete token values + a restrained/crisp/playful motion personality and rare approved delight moments. If the Stitch MCP is connected, offer to generate a design system + key screen drafts from that block; adapt any output to the tokens. Show the result to the user.

## Phase 5 — MVP plan

Generate `docs/mvp-plan.md` from its template:
- **M0 Scaffold** (as templated), **M1 core value system end-to-end** (fill 3–5 concrete tasks plus recovery/instrumentation/one retention loop when justified; the interview's wedge belongs inside M1 and must be exceptionally well executed), **M2 onboarding + paywall**, **M3 polish + gates + store + release**, and recurring **M4 published-app operations** per `docs/playbooks/post-launch.md`.
- Fill the **Scope Fence** with 5–10 explicitly excluded features (likely:
  accounts/social, second features, admin panels, and — for an app-first stack — a web
  version). For SwiftUI-first, Android is a named post-iOS `/port-android` backlog item,
  not part of M0–M3. For an explicitly selected Expo app, include or exclude Android
  according to the approved product scope rather than adding it mechanically. For
  **web-first**, a native app is the exclusion instead, and M3 replaces store/release work
  with the web launch gates: Core Web Vitals and WCAG numbers from the "Web" sections of
  the performance and accessibility checklists, indexability (sitemap, robots, canonical,
  validated structured data), and legal/privacy routes live. Seed every exclusion into
  `docs/backlog.md`.

If running under Claude Code, spawn `spec-consistency-reviewer` again against the
finished `docs/mvp-plan.md` (milestones and Scope Fence) before asking for approval, and
fold its findings in.

**Gate 5:** user approves the plan. This is the scope contract you will enforce for the rest of the project.

## Phase 6 — Bootstrap & build

1. Run `python3 scripts/factoryctl.py doctor`. `asc`, Firebase CLI, Wrangler and Xcode are required for v2 infrastructure; screenshot tools may degrade to their documented fallback. Web-first needs Node, Firebase CLI, and Wrangler only — `asc`/Xcode gaps are not blockers there. Never install or authenticate silently.
2. `git init` (if needed), scaffold the project — **Expo RN:** `npx create-expo-app@latest` + expo-router template, install baseline deps from `docs/stack.md`; **SwiftUI:** guide the user through Xcode project creation (you cannot create .xcodeproj), then add SPM baseline deps; **Web:** `npx create-next-app@latest` (App Router + TypeScript + Tailwind), then install baseline deps from `docs/stack.md`.
   For SwiftUI, `xcodebuild`/`simctl` remain the baseline. When XcodeBuildMCP/Build iOS
   Apps is connected and the full project exists, prefer it for scheme/simulator discovery,
   build/launch, accessibility-tree UI control, screenshots, and logs.
   If Expo is selected, include the `/factory-setup --expo-tools` profile, the user-level
   Expo MCP/OAuth data flow, the SDK 54+ project-local `expo-mcp` dev dependency and MCP
   start script, and their approval/security-model impact; SDK <54 is an upgrade/backlog
   gate.
3. Render `templates/factory-infrastructure/template.json`: copy `web/`, `functions/`, `r2-worker/`, and root Firebase config, then replace only the declared `__APP_NAME__`, `__APP_SLUG__`, `__SUPPORT_EMAIL__` tokens. Verify no template token remains. **Web-first:** the Next.js app is the product surface and owns `/`, `/support`, `/privacy`, and `/terms`, so skip the template's `web/` copy and its Hosting SPA rewrite — copy `functions/` and `r2-worker/` only, and record the framework/host decision (`docs/stack/web.md`) in `docs/decisions.md`.
4. Generate the project `README.md`: pitch; current milestone/status; shipped feature summary; stack and requirements; setup/run/test commands; concise mobile/web/Functions/R2/asc architecture; development/release workflow; links to canonical docs.
5. Provision Firebase per `docs/playbooks/firebase.md`: CLI-create dev/prod and iOS/web apps, initialize emulators, deploy deny-by-default rules + Functions + Hosting to dev. Create a `waiting_human` status card for Blaze/APNs authority; never automate billing.
6. Provision R2 dev/prod buckets and the read-only Worker per `docs/playbooks/cloudflare-r2.md`; verify PUT/POST/DELETE return 405 and no credential reaches web/mobile config.
7. **App-first stacks only** — for web-first, skip this step and instead verify the deploy
   path end to end: production build, a preview deploy, `sitemap.xml`/`robots.txt` served,
   and the legal/privacy routes live. Follow `docs/playbooks/app-store-connect.md`: use `asc-cli-usage` and
   `asc-id-resolver` for discovery, then `asc-signing-setup` and (only for the public-API
   gap) `asc-app-create-ui` during approved M0 preparation. Do not load catalog,
   localization, screenshot, pricing, or TestFlight skills until the guided milestone
   reaches that surface. Any external write beyond the approved kickoff plan pauses for
   confirmation in guided mode.
8. Commit `M0: scaffold`, announce **"Working milestone: M1 — <core feature>. Everything else goes to docs/backlog.md."**, and start M1.

Checkpoint after opportunity research, product approval, MVP-plan approval, and bootstrap.
At each checkpoint run `python3 scripts/factoryctl.py recommend refresh` and
`python3 scripts/factoryctl.py recommend list`, then append at most three recommendations
with why/role/risk/delegation, up to ten TODOs, and pending human approvals.

## Boundaries and report

Never invent evidence, copy competitor expression, expose secrets, use
`--dangerously-skip-permissions`, delete resources, run bare `firebase deploy`, or submit
for App Store review. Protected files and unexpected external writes require the
approvals in AGENTS.md. Update canonical docs immediately as decisions/work change; do
not create parallel status documents. Report the opportunity decision, approved
product/scope, chosen stack/monetization, completed setup, blockers/human actions,
current milestone, and exact next action.
